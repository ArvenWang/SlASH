# Project Slash — Phase 1 验收标准

文档版本：v2.0
适用范围：Phase 1 Visual Vertical Slice 与 2026-08-12 3D 视觉重设计
状态：正式质量门槛，后续 Agent、Visual Critic、资产生产、性能验收和 GitHub 交付统一以此为准。

优先级声明：本文新增的“3D 视觉重设计最终质量门”覆盖旧基线中与其冲突的角色、武器、动画、场景和当前状态描述。旧证据只证明当时版本，不自动证明新资产通过。UI 只处理妨碍角色和战斗可读性的部分，不是本阶段主要评分对象。

## 1. 最终目标

Phase 1 不是普通玩法原型。最终交付必须是一段可以独立游玩的正式品质切片：

- 一张雨夜“交通大教堂”企业平台；
- 一名未来赛博剑士；
- 一种宽重型近战敌人；
- 三个固定 Stage；
- 唯一核心动作：点击目标点，沿直线高速突刺，并击杀路径上的全部敌人；
- Web 桌面版为主目标，1080p / 60 FPS；
- 游戏内容可以少，但画面内不能保留明显的 Blockout、Placeholder、假按钮、假动画或技术 Demo 质感。

一句话目标：

> 第一次看到真实运行画面的人，应认为这是一个范围很小但已经进入商业制作阶段的游戏，而不是一个 Three.js 练习场景。

## 1A. 3D 视觉重设计最终质量门（2026-08-12）

### 1A.1 最终目标

本轮不是简单“换一个更精细的 GLB”，而是交付一条能长期更换角色、武器、动作和关卡外观的正式 3D 生产链。最终必须同时成立：

- 保留已认可的 V5 黑曜主角、朱红重装敌人和 Transit Cathedral 风格；
- 主角、敌人、刀具、骨骼和动画在概念图、独立 Lab 与真实战场中保持一致；
- 生产战场实际使用通过验收的 GLTF 角色，不允许继续用程序化角色冒充新模型成果；
- 更换符合规范的角色或武器时，只新增/替换资产定义、骨架映射和动画映射，不修改 Gameplay 规则；
- 背景退为氛围层，平台与角色成为第一视觉层级；
- 每个阶段只做一次针对性小验证，相关代码未改变时不重复旧机制、长稳或全浏览器验证；全部完成后只做一次整体战场验收。

### 1A.2 一票否决门

以下任一项失败，本轮 3D 视觉重设计直接判定为未完成：

| 编号 | 硬门 | 失败条件 |
|---|---|---|
| VR-H01 | 正式建模输入 | 主角或敌人缺少前、左、后、右四视图；视图不是同一比例/同一服装；没有标准 A-Pose；身体与武器未分离；或缺少材质分区与关节说明 |
| VR-H02 | 模型忠实度 | 未绑骨模型在正/侧/背/右视图与基准轮廓明显不一致；手脚、肩髋、头盔或敌人胸肩识别块发生生成错误；或仍呈现通用 AI 科幻士兵造型 |
| VR-H03 | 骨骼与蒙皮 | 骨架语义依赖 `bone_7` 等不透明名字写死在角色实现中；髋、脚、手或根骨映射错误；标准压力姿势出现肢体分离、塌陷、明显穿模或错误扭转 |
| VR-H04 | 动画闭环 | 主角或敌人的必需动作缺失；动作仍由整体旋转/缩放冒充；出现滑步、沉地、Pose Pop、错误关节轴、武器脱手或模型在 Lab 与战场表现不一致 |
| VR-H05 | 武器比例、刃向与握持 | 主角武器总长不在身高 `58–66%` 范围且无书面例外；刀柄没有进入掌心；腕—掌—护手次序错误；开刃方向与当前持刀姿势/斩击平面相反；主/副手握点缺失；或刀尖/拖尾锚点不随真实武器运动 |
| VR-H06 | 游戏内一致性 | 结构检查通过但任一正式动作仍出现半身沉地、悬空、断肢、错误朝向或动态包围盒裁切；生产 Registry 没有指向验收通过的新 Provider |
| VR-H07 | 模块替换 | 更换同规格模型或武器仍必须修改 Gameplay、碰撞、敌人行为或 Ability 代码；原始骨骼名散落在 Skeleton Profile 之外 |
| VR-H08 | 死亡兼容 | 新敌人无法进入现有延迟切口、分离和尸体流程；或切割表现退化为立即隐藏、缩放消失、随机散架 |
| VR-H09 | 场景层级 | 背景轨道、巨拱、列车或城市亮度/体量继续压过平台与角色；平台仍读成大块均匀黑面、测试方格或均匀镜面 |
| VR-H10 | 真实性与安全 | API Key、下载临时链接或账号信息写入仓库/日志；用概念图、静态渲染或 Lab 单帧冒充真实战场完成；生成资产来源和用途未记录 |

### 1A.3 角色模型质量门

正式角色必须依次通过未绑骨模型、Rig 压力姿势、动画关键帧和生产战场四层检查：

1. **四视图注册**：以头顶、足底和身体中心统一注册；肩线、最窄腰、胯点、膝点和四肢外轮廓逐视图平均偏差不超过身体高度 `3%`，局部轮廓偏差 P95 不超过 `5%`。Raw Hausdorff 最大值继续保留在报告中，用于发现分指、抗锯齿等孤立异常，但不替代 Grip 近景与人工轮廓判断。
2. **连续人体**：肩、肘、腕、髋、膝、踝必须有可变形结构；不得存在端盖、浮动肢体、融合双腿、手指粘连、内外翻脚或藏在身体里的手臂。
3. **压力姿势**：至少检查 A-Pose、双臂前举、双臂过头、深蹲、左右弓步、最大步幅、持刀 Ready、Dash/Run 极值。蒙皮不能出现体积崩塌、甲片撕裂或肢体断开。
4. **资产预算**：Hero LOD0 目标 `8k–16k triangles`，Enemy LOD0 目标 `6k–12k triangles`；允许为连续轮廓合理偏离，但必须有实测性能依据。角色主体尽量不超过 2 个 SkinnedMesh、3 套材质和 2K PBR 贴图；远景使用 LOD/KTX2 或等效降级。
5. **64px 轮廓**：主角仍能读出头、腰腿、刀臂和刀；敌人仍能读出宽胸、重肩、短重武器；即使转灰度也能区分敌我。

### 1A.4 标准骨架与模块替换门

- 每个模型必须通过 `SkeletonProfile` 映射到统一语义：Root、Hips、Spine、Chest、Neck、Head、左右 Shoulder/UpperArm/Forearm/Hand、左右 UpperLeg/LowerLeg/Foot；可选 Toe、Finger 和切割 Landmark 单独声明。
- 模型 Provider 不得直接引用生成器的随机骨骼名；原始名字只能出现在资产专属 Skeleton Profile 中。
- Gameplay 继续拥有唯一 Root Position；动画 Clip 必须为 In-place，Presentation 只对齐视觉姿态。
- 角色模型、Skeleton Profile、Animation Set、Weapon Loadout、Material Variant 与 Death Profile 必须为独立配置。
- 至少用一个非生产 Fixture 证明：替换同规格模型后，Gameplay、Ability、Enemy Behavior 和 Level 文件无需修改，角色仍可完成 Idle、Action、Hit、Death 与武器挂载。

### 1A.5 武器与手部验收门

- 主角武器总长为身高 `58–66%`；首轮比较 `58% / 62% / 66%`，以真实 Gameplay Camera 下的比例、轮廓和动作轨迹确定最终值。
- 建议刀刃（护手至刀尖）为身高 `47–54%`，刀柄为 `10–13%`；任何偏离必须有画面证据和用户确认。
- 武器是独立资产，至少暴露 `primary-grip`、`secondary-grip`、`guard-center`、`blade-base`、`blade-tip` 与 `trail-edge` 语义锚点。
- 主手必须通过层级挂载保持握点误差接近 0；双手动作中副手掌心到 Secondary Grip 的误差不得超过角色身高 `1%`。
- Ready、Anticipation、Dash、Arrival、Recovery、Vector Focus 和 Death 均需提供手部近景；不得出现刀柄悬在掌外、穿过手腕、护手切入掌心或刀身脱离手臂运动。
- 上述近景必须同时显示刀根—刀尖长轴与刀脊—开刃侧轴；开刃侧要在刀身两面和 Gameplay Camera 中保持同一物理侧，不得因观察方向改变而视觉翻面。Ready/Recovery 的刃面朝向下一次安全斩击外侧，Dash/Chain 的刃面必须与实际斩击平面一致。
- 刀刃发光不得掩盖刀柄、手掌和前臂；Gameplay Camera 下能够同时看清角色身体与完整刀线。

### 1A.6 动画质量门

主角正式动画集：

- Combat Ready、Micro Turn；
- Dash Anticipation、Dash Travel、Arrival、Recovery；
- Vector Focus Activate、Selection Loop、Chain Slash 01/02/03；
- Hit（若玩法使用）与 Death。

敌人正式动画集：

- Idle、Turn、Run、Threat、Contact Attack、Recovery；
- Hit Left/Right、Delayed Cut Hold、Separation Transition、Fall/Death。

共同要求：

- 站立脚与地面距离误差不超过角色身高 `0.5%`；接触阶段不得肉眼可见滑步。
- 生产移动速度与 Run 步幅误差不超过 `10%`；动画相位可错开，但不能改变 Gameplay 位置。
- 状态切换不得出现大于身体高度 `1%` 的瞬间 Root 跳变；不得出现肉眼可见关节角跳变。
- Lab 必须提供骨骼、动态 Bounds、脚底接触、主副手握点和武器轴 Debug Overlay；“文件有骨骼/Clip”不等于动作通过。

### 1A.7 场景质量门

- 保留 Transit Cathedral 世界观，但 Gameplay Platform 与角色必须成为灰度图中的第一阅读层级；背景平均亮度、局部高光和细节密度均不得压过战场。
- 主拱、轨道和列车只保留能建立场所身份的主次结构；不得在角色密集区域形成粗重切线、头顶压迫带或与刀线竞争的高亮直线。
- 平台必须同时读出大板块、高低差/边框、检修槽、排水沟、维修补丁、干区、湿区和局部积水；湿润不允许整片统一镜面。
- 视觉几何与 Gameplay Collision 分离；替换 Arena/Transit/City/Weather/Lighting 模块不得改变关卡规则。
- Environment Lab 通过后只进入一次真实 Stage 1/3 对照；平台或背景未再修改时不重复角色、玩法和长稳验证。

### 1A.9 分节证据与验证节奏

证据统一写入 `validation/visual-redesign/`：

```text

model/        未绑骨 Turntable、四视图叠加、64px 轮廓、资产报告
```

验证规则：一个小节完成后只运行覆盖该小节的最小真实验证；已通过且相关实现未改动的项目不重复。角色、场景与正式 Provider 全部接入后，才执行一次最终综合验证。

## 2. 完成判定

必须同时满足以下条件才允许宣布 Phase 1 完成：

1. 所有“一票否决门”通过；
2. 总评分至少 `92 / 100`；
3. Gameplay、Character、Animation、VFX/Gore、Environment 五个核心分类均不得低于该分类满分的 `90%`；
4. 不存在 P0 或 P1 缺陷；
5. 独立 Visual Critic 不再给出“Blockout、技术 Demo、Asset Demo、角色不可读、特效廉价”中的任何一项结论；
6. 自动化、真实浏览器、生产构建、截图/录像、性能报告和许可证清单齐全；
7. 用户完成最终真人试玩与视觉确认。

代码能够编译、浏览器能够打开、Dash 能够移动，都只算基础工程完成，不等于 Phase 1 完成。

## 5. 核心游戏性验收（12 分）

### G-01 输入响应

目标：点击后主观上立即响应。

- Pointer/Touch 输入到逻辑进入 Dash：不超过 1 个固定逻辑 Tick；
- 输入到首个可见反馈：不超过 1 个显示帧；
- 100 次连续点击测量中，视觉响应 P95 不超过 `33ms`；
- 不允许等待角色完整转身后才发动。

证据：浏览器 Performance Mark JSON、100 次输入统计、60 FPS 与慢放录像。

### G-02 Dash 规则

- 目标距离无人工上限，只受 Arena / Wall 限制；
- Transit 时间随距离变化并钳制在 `35–110ms`；
- Dash 全程无敌；
- 目标越界时钳制到合法边界，不能无响应；
- 路径必须是单一直线，禁止弧线、自动寻路或绕行。

证据：自动化边界测试、可视化 Debug 路径、实际浏览器录像。

### G-03 多杀与碰撞

- 使用 Swept Segment / Capsule，不依赖单帧碰撞；
- 同一直线上的 1、5、20 个敌人必须全部击杀；
- 60、120、144 FPS 下结果一致；
- 斩杀半径必须可调，且视觉刀线与逻辑命中区域一致。

证据：自动化测试、三种帧率回放、`render_game_to_text` 状态。

### G-04 Recovery 与 Input Buffer

- Recovery 默认 `120ms`，可调范围 `80–180ms`；
- Recovery 期间玩家可以死亡；
- 只保存最后一个有效输入，不形成长队列；
- Recovery 结束后，缓存输入立即执行。

### G-05 死亡与重开

- 非无敌期间敌人有效接触即死；
- 判定后立即产生死亡反馈；
- 从判定死亡到重新可操作应 `< 1 秒`；
- 不弹确认框，不出现额外 Loading；
- 点击允许跳过剩余死亡展示。

### G-06 三关流程

- Stage 01 / 02 / 03 分别为 8 / 12 / 18 名敌人；
- 同一地图，通过出生位置、节奏和速度提升压力；
- 杀光敌人即过关；
- 三关可以从头到尾完成，不需要 Debug 操作；
- 第三关应自然产生 3、5 和更高 Multi Kill 的机会。

## 6. 镜头、灯光、环境与构图验收（13 分）

### V-01 镜头构图

在 1920×1080、2560×1440、1366×768 三种桌面尺寸下：

- Arena 四条边完整可见，并保留安全留白；
- Gameplay Space 占画面面积约 `55–72%`；
- 远景城市占画面高度约 `22–35%`；
- 不是纯俯视，可以读出胸腔、腿部、持刀姿势和角色前后关系；
- 镜头不传统跟随玩家；
- Dash 时仅允许微量 Directional Kick、Zoom 和 Exposure，不能影响落点判断。

证据：三分辨率空场、战斗、Multi Kill 截图及叠加安全框。

### V-02 四层空间

画面必须同时存在：

1. Foreground：平台边框、轨道结构或近景设施；
2. Gameplay：清晰、低障碍的 Arena；
3. Midground：巨型拱架、列车、维护结构；
4. Background：至少三层高度与密度不同的城市，并受距离雾控制。

失败示例：大片无意义黑墙、重复方块城市、列车像玩具、背景亮度高于刀线。

### V-03 企业视觉语言

必须形成一致的重复规则，例如：

- 斜切角；
- 三道凹槽；
- 橙色安全灯；
- 统一编号与维护标识；
- 相同的金属/混凝土/发光材质体系。

不能依靠鸟居、灯笼、汉字拼贴或随机霓虹制造“赛博朋克”。

### V-04 湿地材质

- 地面不得像灰色方格测试板；
- 至少能读出干区、湿区、积水、排水槽、接缝和局部维修补丁；
- 积水 Roughness 目标 `0.08–0.15`，干区 `0.3–0.45`；
- 反射不能是均匀镜面；
- Slash、人物灯光和列车灯应在湿地上有方向正确的反应；
- 不能用随机黑色烟斑冒充湿润变化。

### V-05 色彩与亮度层级

- 环境：Graphite / Dark Blue / Low-saturation Cyan；
- 主角：冷白 / 青白；
- 敌人：受控红橙；
- 血液：高饱和真实红；
- 刀锋与 Slash Core 必须始终是画面最高亮度；
- 纯白过曝区域不得超过画面像素的 `1%`；
- 禁止紫蓝粉全部高饱和的 Neon Soup。

证据：原图、灰度图、亮度直方图、Bloom Mask。

## 7. 主角与敌人造型验收（18 分）

### C-00 概念锁定与建模一致性

正式建模前必须先锁定项目内概念基准。2026-08-12 起，V5 继续作为视觉风格与角色身份基准，但不能直接作为最终生产输入；正式生产基准必须升级为 V5R 四视图 A-Pose、独立武器规格、材质分区和关节说明。V4 及更早版本只保留为迭代记录。

- `art/characters/concepts/hero-turnaround-v5.png`；
- `art/characters/concepts/enemy-turnaround-v5.png`；
- `art/characters/concepts/hero-action-sheet-v2.png`；
- `art/characters/concepts/enemy-action-cut-sheet-v2.png`。

概念与模型必须满足：

- 前、左、后、右四视图必须为同一角色、同一服装和同一比例；身体图不携带武器，武器使用独立正交规格图；不允许用气氛图代替建模依据；
- 主角采用细长、前卫、黑色切面轮廓与冷白长刀；敌人采用宽重切面轮廓与红橙倒 V 胸肩识别块；
- 使用原创的低至中多边形大切面语言，不复制《师父》或任何现有游戏的角色、服装、头盔、武器和动画；
- 在正面、侧面、背面正交叠加检查中，先以头顶/足底和身体中心做统一缩放、平移注册；肩线、肩冠最大宽、最窄腰、胯点、膝点的左右活体轮廓边界，逐视图平均偏差不得超过 `3%`、局部轮廓偏差 P95 不得超过 `5%` 身体高度。Raw Hausdorff 最大值仍须如实报告；V5 必须使用重新标定的读点，数值工具不得把 Rig pivot 当作可见人体边界，也不得复用 V4 或更早版本的人工读点；
- 武器硬门必须使用真实世界长度并与独立 Weapon Definition 对照：主角武器总长必须为身高的 `58–66%`，敌人短刀必须记录真实世界长度及其书面设计区间。禁止把持刀二维投影长度直接当作真实长度；
- 模型可以为动画、远镜头可读性和 Web 性能做局部工程调整，但必须记录原因，不能借优化之名改回通用科幻士兵；
- 动作状态机的关键 Line of Action 必须能对应动作基准图，不能只让整个模型平移、缩放或瞬间旋转。

证据：概念版本记录、三视图模型叠加图、Turntable、64px 轮廓表、动作关键帧对照，以及分开列出的数值门、世界长度门与人工主观门。自动量测只能报告数值门，不得自行伪称主观美术门通过。

### C-00A V5 正式建模视觉门

V5 的角色通过必须同时满足三层检查，任何一层都不能由另一层代替：

1. **近景建模层**：1024×1024 Character Lab 的正面、侧面和 3/4 视图中，颈肩、胸腰、髋腿、肘腕、膝踝必须形成连续人体；不得出现暴露的圆形端盖、关节插头、悬浮甲片、积木鞋、棍状手臂或基础几何拼装感。
2. **动作轮廓层**：主角 Ready 必须双脚真实落地、骨盆下沉、胸肩前压、刀柄贴近腰侧；敌人必须是带重量的冲跑，而不是站立平移、整齐复制或身体接近水平的爬行姿态。
3. **真实战场层**：固定生产镜头中，主角必须能同时读出头、躯干、双腿和整片发光刀，不得只剩一团刀光；同屏至少 8 名敌人时，应直接看出不少于 4 种步相、肩线和武器高度组合。

主观失败词包括：`Blockout`、`积木人`、`胶囊人`、`玩具机器人`、`关节断裂`、`站桩`、`复制姿势`、`刀光吞人`。只要任一词仍适用于真实画面，H-01 或 H-05 就不能通过。

### C-01 主角 Hero Asset

- 最终必须为经过重制的正式模型，不接受基础几何体拼接；表面可以保持多面几何风格，但人体比例、关节过渡和剪影必须先成立；
- 高挑、窄腰、长腿，具有清晰肩线和头部识别点；
- 头部使用未来传感器/多目视觉语言，不复制现有 IP；
- 刀具总长为身体高度的 `58–66%`，首轮以 `58% / 62% / 66%` 三档在 Gameplay Camera 中比较；
- 黑色主体必须通过近黑柔性层、深石墨大甲面和克制的冷白能量三类材质建立层次，不允许用碎片装甲与随机饰线堆细节；
- 武器必须是明显短于身高、极薄轻弯的独立能量刀；允许使用克制的深色刀脊/刀身承托一条清晰的单侧发光刃，以便明确开刃方向，但不得出现粗重黑芯、只剩显微级亮边或从 Gameplay Camera 看不出哪一侧开刃；并必须提供主/副握点、护手、刀根、刀尖和拖尾锚点；
- 发光面积应克制，不能把人物变成青白光球；
- 1080p Gameplay 中角色屏幕高度至少 `50px`；
- 在 64px 高的纯轮廓测试中仍能识别头、肩、腿和刀。

证据：前、后、侧、3/4 Turntable；材质拆解；64px Silhouette Sheet；Gameplay 截图。

### C-02 敌人正式模型

- 肩、胸、前臂明显比主角宽重；
- 在不看颜色时，仅靠轮廓也能与主角区分；
- 红橙识别块至少覆盖头、胸或肩部之一，不能只依赖一个红点；
- 造型必须支持清晰的身体切分和机械碎片；
- 不得保留普通现代枪兵或卡通机器人语义。
- 冲跑时胸腔总前倾应保持为明确冲锋姿态，不能因父子关节旋转叠加而接近水平；抬腿、落脚和刀臂必须仍能看出人体结构。

### C-03 Web 资产预算

目标范围，不是以牺牲效果为代价的绝对数字：

- Player LOD0：目标 `8k–16k triangles`；
- Enemy LOD0：目标 `6k–12k triangles`；18–20 人同屏时优先保留大轮廓和关节连续性；
- 三角面数量不是独立通过条件：不得通过无意义细分凑数，也不得以 Web 性能为由保留明显的 1k 级基础块状模型；
- 角色正式材质尽量控制在 2–3 套；
- 贴图使用 KTX2 / Basis，远镜头不保留无效 4K 细节；
- 必须提供 LOD 或距离降级策略；
- 所有第三方资产必须经过轮廓、材质、配色和比例重制，禁止原样拖入。

## 8. 动作与动画验收（20 分）

### A-01 主角动画集

至少包含：

- Combat Idle；
- Micro Turn；
- 5–25ms 的视觉 Anticipation；
- Dash Pose；
- Arrival / Landing；
- 80–180ms Recovery / Sheathe；
- Player Death。

要求：

- 动作必须来自同一套身体语言；
- 转向不能瞬间机械旋转；
- Anticipation 不能增加实际输入延迟；
- Dash 不是播放跑步动画；
- Recovery 看起来是收刀/稳定身体，而不是等待 CD；
- 动画切换不能出现明显 Pose Pop、穿模或武器脱手。

### A-02 敌人动画集

至少包含：

- Idle；
- Locomotion；
- Turn；
- Contact Attack / Threat Pose；
- Hit Freeze；
- Delayed Cut；
- Body Separation / Fragment Landing。

要求：

- 步幅与移动速度误差不超过 `10%`，不得滑步；
- 转身有平滑过渡和身体倾斜；
- 所有敌人不得机械地朝玩家平移；
- 同屏 20 名敌人允许动画相位错开，避免完全同步。

### A-03 时间线验收

目标时间线：

| 时间 | 事件 |
|---:|---|
| 0ms | 输入 |
| 0–25ms | 刀锋亮度 Spike / 微量压身 |
| 15–110ms | Dash Transit |
| 20–130ms | 3–4 层 Afterimage / Slash Core |
| 40–100ms | Enemy Cut Seam 出现 |
| 120–230ms | 身体分离 |
| 130–300ms | 血液、火花、碎片 |
| 80–180ms | Arrival / Recovery |
| 180–400ms | Trail 衰减 |

证据：正常速度录像、4× 慢放、逐帧时间标注。

## 9. Dash、击杀、血液与肢解验收（20 分）

### FX-01 Slash Line

- 必须是单一、极细、笔直的冷白 Core；
- 1080p Core 建议为 `1–3px`，外围 Cyan Glow 不超过约 `8px`；
- 不得变成粗激光柱、弧形剑气或闪电；
- 湿地必须捕捉方向正确的短暂反射；
- 视觉位置与真实命中段一致。

### FX-02 Afterimage

- 只使用 `3–4` 层；
- 从起点到落点按时间排列；
- 透明度和细节逐层降低；
- 不能像复制了四个完整角色；
- 正常 Dash 后约 `350ms` 内清理。

### FX-03 敌人死亡

必须包含并按顺序发生：

1. 玩家穿过；
2. 敌人短暂保持站立；
3. 切口/热边出现；
4. 身体向斩击方向错位；
5. 身体分离；
6. 真实红血、火花和机械碎片爆发；
7. 大块尸体落地并保留到本 Stage 结束。

不接受立即消失、缩放到零、统一爆炸、整个角色像积木随机散架。

### FX-04 血液

- Blood Spray 必须具有斩击方向；
- Blood Mist、较大液滴、地面 Decal 分层存在；
- Decal 形状不规则，不能是圆形或简单椭圆；
- 血池与尸体位置对应；
- 血液为真实高饱和红，但不能盖住整个战场；
- Decal/粒子/碎片使用对象池并有上限。

### FX-05 环境反应

Dash 附近至少实现三项：

- 雨线被方向力带开；
- 雾被短暂切开；
- 积水或湿地出现扰动/反射；
- 松散粒子沿 Dash 方向偏移；
- 局部灯光/曝光产生极短响应。

### FX-06 Multi Kill

- 1 Kill：普通层级；
- 3 Kill：增加音效层和微量镜头反馈；
- 5 Kill：增强 Slash 保持与 Exposure；
- 8+ Kill：允许 40–70ms Hero Moment；
- 不使用遮挡画面的 DOUBLE KILL / PENTA KILL 巨大文字。

## 10. 音效与镜头反馈验收（5 分）

- Rain、City、Blade Hum、Dash、Air Whoosh、Blade、Flesh、Metal、Blood、Death、Multi Kill 均有独立层；
- Dash 不能只播放一个 `whoosh.wav`；
- 输入到声音首个瞬态 `< 50ms`；
- 同类击杀至少提供 6 组微变化，避免连续重复；
- 多敌人同时死亡时不得削波或爆音，Master Peak 不超过 `-1 dBFS`；
- 镜头反馈不能影响方向判断或引起持续眩晕；
- 支持关闭声音，浏览器自动播放限制下不报错。

## 11. Web 性能、兼容性与加载验收（7 分）

### P-01 1080p High 硬目标

测试机基线：Apple M1 Pro 16-core GPU，当前 Chrome 稳定版。

Worst Case 场景持续 60 秒：

- 20 名敌人；
- 一次击杀 8 名；
- Rain、Steam、Blood、Fragments、Corpses、Camera FX、Post FX 同时存在；
- 平均 FPS `>= 59`；
- P95 Frame Time `<= 18.33ms`：即 60Hz 一帧 `16.67ms` 加 10% 浏览器调度容差；必须同时保存同机空白页 rAF 基线与游戏原始值，不允许平滑、截断或删除慢帧；
- P99 Frame Time `<= 24ms`；
- 除首次资产加载外，不允许单帧超过 `50ms`；
- 10 分钟运行后，内存不能持续无上限增长。

### P-02 分辨率与降级

- 2560×1440 High：平均 FPS `>= 55`；
- Compatibility 档必须保留同一 Art Direction；
- 允许降低粒子、阴影、反射和 Post FX；
- 不允许降级后变成无灯光、无材质的低质量 Demo；
- 触摸输入必须真实可用，移动端允许降低画质。

### P-03 加载

- 初始压缩下载 Soft Target `< 50MB`，Hard Target `< 80MB`；
- 冷加载必须有正式 Loading 画面和真实进度；
- 50Mbps 网络下进入可操作状态目标 `< 8 秒`；
- 不能在首次 Dash 时临时加载关键 VFX/音效造成卡顿。

### P-04 浏览器

至少验证：

- Chrome 最新稳定版；
- Edge 最新稳定版；
- Safari 最新稳定版；
- WebGL2 Compatibility 路径；
- 浏览器 Resize、Fullscreen、DPR 变化和后台恢复。

## 17. 执行顺序

必须按以下顺序收口：

1. 锁定主角/敌人 V5R 四视图、材质/关节、独立武器和动作规格；
2. 生成并筛选未绑骨模型，完成清模、材质、LOD 与切割准备；
3. 建立标准 Skeleton Profile、Rig、正式 Clip、手脚 IK 修正和 Weapon Definition；
4. 在 Animation Lab 完成角色、动作、握持和动态落地门；
5. 弱化 Transit/City 背景并精细化 Arena Platform；
6. 通过正式 Provider 接入战场并证明模型/武器可替换；
7. 只回归受影响的 Dash / Kill / Cut / Gore / Environment Reaction；
8. 执行一次最终整合、性能、独立 Critic 与用户真人验收；
9. 证据包、许可证、最终提交并同步 GitHub。

不得通过继续增加关卡、技能、Boss、Roguelike 或 UI 来绕开前五项。
