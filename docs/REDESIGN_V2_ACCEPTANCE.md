# Project SlASH — Redesign V2 Acceptance

> 状态：当前验收事实源  
> 版本：v2.0  
> 更新日期：2026-08-13  
> 说明：旧 `FULL_GAME_ACCEPTANCE.md` 只保留对未改动战斗机制的历史证据；凡与本文件冲突的流程、UI、视觉和验证项全部失效。

## 1. 完成原则

- 自动化只证明规则和确定性；真实截图证明玩家实际看到的画面；真人判断证明节奏和审美。三者不得互相冒充。
- 每个小节完成后只运行该小节的定向验证。
- 整体迁移完成后运行一次完整 Run、构建和必要回归。
- 已通过且本次没有修改的能力、敌人、Boss、性能或浏览器范围不重复验证。
- 任何旧测试若保护的是已废弃体验，必须删除或改写，不能为了保持旧测试绿色而保留错误产品。

## 3. 第一实施阶段：技能获取与 UI

### V2-S01 — 候选生成

- 每次奖励状态恰好 3 个不同、合法、可选择的技能 ID。
- 相同 `Seed + rewardIndex + ownedSkills + poolVersion` 结果完全一致。
- 已拥有且不可叠加的技能不再出现。
- 依赖未满足的技能不出现。
- 连续 10,000 次生成不得出现少于 3 张、重复卡、非法卡或不可结算卡。
- 候选不足时走正式替代奖励规则，不能填充假技能。

### V2-S02 — 选择与生效

- 选择仅接受当前候选之一。
- 一组候选最多结算一次；重复命令结果为 `ignored`。
- 选中后立即写入本局构筑并清空候选状态。
- 至少使用一个现有真实技能验证“选择前不生效、选择后下一场生效”。
- 选择完成后由 Director 自动进入下一节点，不出现路线选择页面。

### V2-U01 — 启动与主流程

- Title 无操作保持至少 60 秒且不进入 Combat。
- `开始游戏` 一次操作直接进入第一场 Combat。
- 有合法存档时才显示 `继续游戏`。
- Title 主区不出现协议、威胁等级、Boss 练习、档案和系统说明。

### V2-U02 — 三选一页面

- 页面恰好 3 张可操作卡，无第四个主要动作。
- 每张卡只显示名称与一行效果；效果文字在目标宽度内不被裁切。
- 不显示完整树、连线、点数、Tier、Prerequisite、Effect、Trigger、Limit 或路线信息。
- 键盘、鼠标和触控都能完成一次选择；最小触控目标 44px。

### V2-U03 — 单语言与禁止项

- 默认玩家文案使用简体中文。
- 技能名允许整项使用英文；同一名称不得“中文 / English”并排。
- 正式 UI 中以下字符串数量必须为 0：`Draft`、`Committed`、`SP`、`Seed`、`Effect`、`Trigger`、`Limit`、`Prerequisite`、`INBOUND`、原始 Encounter/Wave ID。
- `.skill-tree`、`.run-map`、`.route-card`、旧 Planning 主面板在正式玩家流程中不得渲染。

### V2-U04 — HUD 与胜负

- Combat HUD 只保留生命、能量、大招可用状态和当前必要目标。
- 能量从 0 到 100 的变化可见；100 时空格进入 Vector Focus。
- 失败与胜利默认页只提供结果、重开和返回主页；不默认展示统计表。

### 本阶段小规模验证

只运行以下一次：

1. 三候选生成、合法性、选择一次性和确定性单测；
2. 受影响的 Campaign / Save / Replay 定向测试；
3. 一次真实浏览器流程：Title → Combat → Clear → 三选一 → 下一场 Combat；
4. 检查该流程截图、`render_game_to_text` 和 Console。

本阶段不重跑敌人全矩阵、Boss 400 次、长时性能、全浏览器矩阵或全部技能 Hook。

## 4. 第二实施阶段：场景

### V2-E01 — 干净高台

- 正式战斗运行时不创建 City、Transit、Train、Weather 或旧厚平台模块。
- 视觉平面在 1920×1080、1366×768、390×844 三个画幅均覆盖整个背景。
- 正常战斗构图中看不到平台外部世界；允许在坠落或特殊镜头下短暂看见高台侧面。
- 逻辑 Arena 边界、Spawn 和碰撞不因视觉平面扩大而改变。

### V2-E02 — 镜头

- 保留斜俯视方向。
- 以当前战斗画面为基准，可见世界宽度和深度至少扩大约 1.5 倍。
- Resize 后根据画幅重新计算构图，不只更新 `aspect`。
- 主角、普通敌人、Projectile 和危险区仍可辨识；拉远不能以牺牲战斗信息为代价。

### 本阶段小规模验证

只运行场景创建/释放与 Camera Fit 定向测试，并检查三个目标画幅的战斗截图和 Console。未改动的战斗规则不重跑。

## 5. 后续实施阶段：几何体角色与重力

### V2-P01 — 真实垂直物理

- Player 与 Enemy 状态包含 `height/y`、`verticalVelocity`、`gravity`、`grounded/supported` 等明确事实。
- 固定步中自由体速度按重力持续变化；接触支撑面后按定义落地或进入悬浮平衡。
- 关闭悬浮支撑后角色会下坠；越出高台支撑范围后不能被表现层强制放回 `y=0`。
- 同 Seed / Command 在不同渲染帧率包装下保持相同 Gameplay Hash。

### V2-P02 — 可见运动

- 主角轮廓为三角形，敌人为方形基础轮廓。
- Idle、Move、Telegraph、Attack、Hit、Death 六类状态至少具有可观察的旋转、高度、缩放或颜色变化。
- 连续取样中，活体 Idle 的轮廓或高度必须变化，但 Gameplay 水平位置可以不变。
- 攻击预警与攻击动作不能错误路由到移动动作。

## 6. 整体完成门

前三个近期阶段完成后运行一次：

1. TypeScript、生产构建、架构边界与 whitespace；
2. Title → 完整标准 Run → Victory；
3. 至少三次三选一，并确认技能真实改变战斗；
4. Save / Continue 与 Replay Hash；
5. 桌面与移动各一次核心流程；
6. 一次最终截图审查和 Console 检查。

几何体角色与重力完成后再追加一次受影响的完整 Run，不回头重复已经封存且未改变的历史验证。

## 7. 必须废弃或改写的旧验收

- `capture-full-game-ui.mjs` 中要求显示 28 个技能节点、28 份完整说明、完整 Run Map 和大量节点的通过条件必须删除或反向改写。
- `capture-campaign-noncombat.mjs` 中要求 Forge 展示完整技能树的条件必须删除。
- `full-game-state.test.ts` 中“玩家选择路线 → 玩家配点 → 确认”的主流程必须替换为“后台选关 → 战斗 → 三选一”。
- `verify-pause-touch-summary.mjs` 不再以完整构筑说明和总结统计为成功条件。
- 动画验收不得只检查 Mixer、Clip 名称或 Controller 状态，必须包含真实战斗镜头下的连续帧可见差异。
